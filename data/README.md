# FaultFalcon datasets

Everything under `data/` is generated by `make ingest` (`python -m ff.ingest.pipeline`) from the
LogHub samples and a fixed seed; the same command always produces the same files.

## The simulated company

A managed-compute platform on AWS with 15 components (full table: `docs/architecture/topology.md`):

```
                       api-gateway (API Gateway + ALB, Lambda authorizer)
                     /        |                 \
              auth-svc     cloud-api ------------ billing-svc --- notification-svc (Lambda + SES)
              /     \      /  |   \     \            |      \
   session-cache  meta-db  |  |  image-svc  usage-queue   billing-db
   (ElastiCache)   (RDS)   |  |      |      (SQS; fed by cloud-api)
                           |  |  object-store (S3)
                  compute-svc  \
                   /   |   \    meta-db
          storage-svc coord-svc meta-db
                 \      (ZooKeeper)
                  node-svc (EC2 fleet; compute-svc and storage-svc run on it)
```

Edges follow the usual AWS patterns: synchronous calls only where a request needs an answer, a
queue between metering (cloud-api) and billing, one database per bounded context, a read-through
Redis cache in front of the session store, stateful services on the EC2 fleet. Nothing is
connected without a reason.

## Files

| Path | Format | What it is |
| --- | --- | --- |
| `raw/loghub/<System>/` | CSV (LogHub) | REAL log samples (OpenStack, Hadoop, HDFS, Zookeeper, BGL, Thunderbird). Never modified. `make data` downloads them. |
| `audit.md` | Markdown | What the real logs contain and how they map to components. |
| `derived/lines_<component>.parquet` | Parquet | Every log line of a component: `ts, level, content, drain_template, is_error, latency_s, http_status, source` (`loghub` = real, `synthetic` = generated). |
| `derived/windows.parquet` | Parquet | Detector windows (error ratio, templates, latency, significant yes/no) per component and stream. |
| `derived/log_events.json` | JSON | Detected ANOMALY / ERROR_SIGNATURE records and the baselines. |
| `telemetry/<component>.log` | text | A readable excerpt of each component's synthetic log around an incident, in its native format. |
| `sim/events.jsonl` | JSON lines | Six months of simulated history: DEPLOY (ppd, test, prod), PATCH (hotfix), ROLLBACK, CONFIG_CHANGE, INFRA_CHANGE (Terraform), TEST_RUN, SECURITY_SCAN. Each change carries a `change_request` (id, author, approver, risk, rollout, rollback plan) and a natural-language `description`. |
| `sim/change_details.jsonl` | JSON lines | The diff hunks of every change (`chg_N`): file, line, symbol, unified diff, config / Terraform key with old and new value, AWS resource. |
| `sim/log_events.jsonl`, `sim/error_signatures.jsonl` | JSON lines | The log-derived records with their final `evt_N` ids. |
| `sim/final_params.json` | JSON | Every component's config and Terraform values at the end of the history. |
| `incidents/INC-NNN.json` | JSON | One incident with its ground truth (below). |
| `incidents/index.csv` | CSV | One row per incident: split, start, alert, severity, title, scenario, category, cause, breaking line. |
| `training/conversations_*.jsonl` | JSON lines | Engineer <-> FaultFalcon dialogues for fine-tuning (train: dev incidents, eval: held out). See `training/README.md`. |

The team's knowledge base (release-train plans, daily change logs, codebase guides, runbooks,
postmortems, topology, patterns) is written to `docs/architecture/`. Every document has a
`Published:` time, and retrieval never shows a document published after the incident under
investigation started.

## Incidents

120 incidents (`INC-001` .. `INC-120`, chronological), 96 `dev` and 24 `heldout` (stratified by
scenario). About 12 sit on anomalies of the REAL LogHub logs (last 72 hours); the rest are
spread over six months with synthetic telemetry. Every incident starts at an ANOMALY the detector
found on its alerting component.

An incident file has three parts:

* what the on-call engineer sees: `title`, `severity`, `detection` (the alarm), `impact`,
  `service` (the alerting component), `incident_start`, `symptom`, `error_templates`,
  `anomaly_numbers`;
* the ground truth: `scenario_type` / `scenario_title` / `category` (code, config, infra, data,
  external), `cause_service`, `cause_event_id` (the change, macro), `culprit_change_id` and
  `culprit` (the breaking line, micro), `contributing_ids`, `decoy_ids` (harmless changes closer in
  time), `blast_radius`, `remediation_ids` (the rollback / revert the team applied at
  `mitigated_at`), `rca` (macro, micro, remediation text) and `action_items`;
* bookkeeping: `split`, `source` (`loghub` or `synthetic`), `anomaly_id`, `scenario_event_ids`.

The model and the retriever never read the ground-truth fields; only the evaluation does.

## Scenarios

About 45 failure classes (`ff/ingest/scenarios.py`), each used for one or more incidents:

* **code**: bad deploys, null dereference after a removed guard, N+1 queries, memory leaks,
  timeout unit bugs, retry storms, a producer shipping a new event schema before its consumer,
  library upgrades, a hotfix patch that serialised requests, release-train cascades two services
  down the chain;
* **config**: DB pool cuts, session-TTL typo, consumer concurrency above the DB connection limit,
  webhook retry storms, circuit-breaker thresholds, a feature flag waking dormant code;
* **infra (AWS)**: RDS max_connections, RDS downsizes and engine upgrades applied at peak, Secrets
  Manager rotation with cached credentials, ElastiCache downsizes / noeviction / security-group
  typos, SQS visibility timeout and redrive, IAM policy losing s3:GetObject, S3 lifecycle expiring
  base images, API Gateway throttling, ALB idle timeout, target-group health checks, ECS memory,
  Auto Scaling max size, Lambda concurrency, EBS throughput, disk shrinks, instance downsizes,
  security groups;
* **data**: blocking migrations, dropped indexes;
* **external** (no change explains it): a customer's traffic spike, an expired customer
  certificate, an S3 regional degradation, SES throttling.

## Inspecting

```bash
make incidents                                   # the incident table
python -c "import pandas as pd; print(pd.read_csv('data/incidents/index.csv').head(20))"
```

```python
import json, pandas as pd
inc = json.load(open("data/incidents/INC-001.json"))
ev = pd.read_json("data/sim/events.jsonl", lines=True)
print(ev[ev.id == inc["cause_event_id"]].payload.iloc[0]["description"])
lines = pd.read_parquet("data/derived/lines_billing-svc.parquet")
print(lines[lines.is_error].content.value_counts().head())
```

Or open the app (`make app`): Timeline, Logs, Knowledge base and Diff tabs show the same data.
